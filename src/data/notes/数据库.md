## 关系模型基础

### 术语

| 术语 | 含义 | 类比 |
|---|---|---|
| 关系 | 一张二维表 | 表 |
| 元组 | 表中的一行 | 记录 |
| 属性 | 表中的一列 | 字段 |
| 域 | 属性的取值范围 | 数据类型 + 约束 |
| 分量 | 行与列的交叉处的一个值 | 单元格 |

### 码（键）

- **候选码**：能唯一标识一个元组的最小属性组。可能不止一个。
- **主码**：从候选码里选定的那一个，作为正式标识。
- **主属性**：包含在任一候选码中的属性；其余叫**非主属性**。
- **外码**：本表中引用另一张表主码的属性（组）。

### 三类完整性约束

| 约束 | 要求 | 由谁保证 |
|---|---|---|
| **实体完整性** | 主码非空且唯一 | DBMS，用主键约束 |
| **参照完整性** | 外码的值要么为空，要么等于被引用表里某个主码值 | DBMS，用外键约束 |
| **用户定义完整性** | 业务规则，如年龄 0~150、成绩 0~100 | 建表时用 `CHECK` / `NOT NULL` 等 |

## 关系代数

### 运算一览

**五个基本运算**（其它都能由它们导出）：

| 符号 | 名称 | 作用 |
|---|---|---|
| ∪ | 并 | 两张表元组合并（要同构）|
| − | 差 | 在 R 中而不在 S 中的元组 |
| × | 笛卡尔积 | 两表元组两两拼接 |
| σ | 选择（selection）| 按条件**挑行**，对应 `WHERE` |
| π | 投影（projection）| 按需要**挑列**，对应 `SELECT 列名` |

**导出运算**：

| 符号 | 名称 | 作用 |
|---|---|---|
| ∩ | 交 | R ∩ S = R − (R − S) |
| ⋈ | 自然连接 | 按同名属性相等拼接，再去掉重复列 |
| ÷ | 除 | "包含全部"类问题的专用武器，对应双重 `NOT EXISTS` |

### 除法的意义

`R ÷ S` 的语义是：**找出 R 中"搭配了 S 里所有值"的那些值**。典型问法是"选修了全部课程的学生""至少选修了某老师全部课程的学生"——看到"全部/all"就该想到除法。

可以这样记：`R(X, Y) ÷ S(Y)` 得到 X 上的取值，使得该 X 与 S 中每一个 Y 都能在 R 里找到。等价于：

```
R ÷ S = π_X(R) − π_X( (π_X(R) × S) − R )
```

即"把所有可能组合减去实际存在的，剩下的就是没配全的，再从未筛过的全集里减掉"。

### 教材例题（原稿记法，保留）

> (3) 检索至少选修"程军"老师所授全部课程的学生姓名(SNAME)。
>
> `(3). ∏SNAME{s  [∏S#,C#（SC）÷∏C#(σTEACHER=‘程军’(C))]}`
>
> (4) 检索"李强"同学不学课程的课程号(C#)。
>
> `(4). ∏C#(C)- ∏C#(σSNAME=‘李强’(S)   SC)`
>
> (5) 检索至少选修两门课程的学生学号(S#)。
>
> `(5). ∏S#(σ[1]=[4]∧[2]≠[5] (SC × SC))`

### 规范写法

设三张表：`S(S#, SNAME, AGE, SEX)`、`C(C#, CNAME, TEACHER)`、`SC(S#, C#, GRADE)`。

**(3) 至少选修了程军老师全部课程的学生姓名**——经典除法：

```
π_SNAME( S ⋈ ( π_{S#,C#}(SC) ÷ π_{C#}( σ_{TEACHER='程军'}(C) ) ) )
```

读法：先取程军教的所有课程号，再拿"学生-课程"表去整除它，得到修全了的学生学号，最后和 S 连接取姓名。

**(4) 李强不学的课程号**——差集：

```
π_{C#}(C) − π_{C#}( σ_{SNAME='李强'}(S) ⋈ SC )
```

读法：全部课程号 减去 李强已选的课程号。

**(5) 至少选修两门课程的学生学号**——自连接 + 条件：

```
π_{S#}( σ_{[1]=[4] ∧ [2]≠[5]}( SC × SC ) )
```

读法：SC 和自身笛卡尔积，同一学生（第 1、4 列相等）且课程不同（第 2、5 列不等），即"至少两门"。

> 第 (5) 题用自连接是因为关系代数没有"计数"，只能用"存在另一个不同的元组"来表达"两门"。SQL 里有 `COUNT`，可以写得更直白（见下）。

## SQL

### 建表：DDL

```sql
CREATE TABLE S (
  `S#`    CHAR(4)     PRIMARY KEY,
  SNAME   VARCHAR(20) NOT NULL,
  AGE     INT         CHECK (AGE BETWEEN 0 AND 150),
  SEX     CHAR(2)     CHECK (SEX IN ('男', '女'))
);

CREATE TABLE C (
  `C#`      CHAR(4)     PRIMARY KEY,
  CNAME     VARCHAR(30) NOT NULL,
  TEACHER   VARCHAR(20)
);

CREATE TABLE SC (
  `S#`    CHAR(4),
  `C#`    CHAR(4),
  GRADE   INT CHECK (GRADE BETWEEN 0 AND 100),
  PRIMARY KEY (`S#`, `C#`),                    -- 复合主键
  FOREIGN KEY (`S#`) REFERENCES S(`S#`),       -- 参照完整性
  FOREIGN KEY (`C#`) REFERENCES C(`C#`)
);
```

> 注意：`#` 在 MySQL 里是**注释起始符**，所以列名要写成反引号包的 `` `S#` ``。教材里写作 `S#` 是记法，实际建表要加引号。
>
> `SC` 的主键是 `(S#, C#)` 复合键——这正好体现了"一个学生一门课只有一条成绩记录"。

### 增删改：DML

```sql
INSERT INTO SC (`S#`, `C#`, GRADE) VALUES ('S001', 'C01', 88);

UPDATE SC SET GRADE = 90 WHERE `S#` = 'S001' AND `C#` = 'C01';

DELETE FROM SC WHERE GRADE IS NULL;
```

### 查询：DQL

**基本结构**：

```sql
SELECT 列名
FROM   表名
WHERE  行条件
GROUP BY 分组列
HAVING 组条件
ORDER BY 排序列;
```

**执行顺序**（和书写顺序不同，常考）：`FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY`。

**聚合与分组**：

```sql
-- 每门课的平均分、选课人数
SELECT `C#`, AVG(GRADE) AS 平均分, COUNT(*) AS 人数
FROM SC
GROUP BY `C#`
HAVING COUNT(*) >= 2;
```

**连接**：

```sql
-- 查每个学生的姓名和所选课程名（内连接）
SELECT S.SNAME, C.CNAME, SC.GRADE
FROM SC
JOIN S ON SC.`S#` = S.`S#`
JOIN C ON SC.`C#` = C.`C#`;
```

**用 SQL 重写上面三道例题**：

```sql
-- (3) 程军老师全部课程都选了的学生姓名：双重 NOT EXISTS（等价于除法）
SELECT SNAME FROM S
WHERE NOT EXISTS (
  SELECT * FROM C
  WHERE TEACHER = '程军'
    AND NOT EXISTS (
      SELECT * FROM SC WHERE SC.`S#` = S.`S#` AND SC.`C#` = C.`C#`
    )
);

-- (4) 李强不学的课程号
SELECT `C#` FROM C
WHERE `C#` NOT IN (
  SELECT `C#` FROM SC
  WHERE `S#` IN (SELECT `S#` FROM S WHERE SNAME = '李强')
);

-- (5) 至少选修两门课程的学生学号（比关系代数直观得多）
SELECT `S#` FROM SC
GROUP BY `S#`
HAVING COUNT(*) >= 2;
```

> 双重 `NOT EXISTS` 的读法：**不存在**一门程军教的课，是**这个学生没选**的。两层否定叠起来就是"全都选了"——和关系代数的除法是同一件事。

## 规范化

### 函数依赖

记 `X → Y`：X 确定 Y。三种要区分的形态：

| 类型 | 定义 | 通俗说法 |
|---|---|---|
| **完全函数依赖** | X → Y，且 X 的任何真子集都推不出 Y | 要靠整个码才能定 |
| **部分函数依赖** | X → Y，但 X 的某个真子集也能推出 Y | 只靠码的一部分就够 |
| **传递函数依赖** | X → Y，Y → Z，且 Y 推不出 X | 绕了一层 |

### 各级范式

| 范式 | 要求 | 消除了什么 |
|---|---|---|
| **1NF** | 每个属性都不可再分 | 表中表、多值单元格 |
| **2NF** | 1NF + 非主属性完全依赖于码 | 部分函数依赖 |
| **3NF** | 2NF + 非主属性不传递依赖于码 | 传递函数依赖 |
| **BCNF** | 每个决定因素都包含码（约束到所有属性，不只非主）| 主属性对码的部分 / 传递依赖 |

**越高越好吗**：范式越高冗余越少，但表拆得越碎、连接越多、查询越慢。**实际工程里常故意"反范式"**——比如订单表里冗余存一份用户名，省掉一次连接。

### 无损连接与保持依赖

> 在关系数据库的规范化理论中，在执行"分解"时，必须遵守规范化原则：**保持原有的依赖关系和无损连接性**。

- **无损连接**：分解后自然连接回去，得到的结果和原来**一模一样**，不能多也不能少（多了是"有损"，少了是丢了信息）。
- **保持依赖**：原来的每个函数依赖，都能在某个分解后的子关系里被推导出来。

两者有时**不可兼得**：达到 BCNF 的分解可能丢掉某些函数依赖，这时工程上常退一步选 3NF。

## 事务与并发

### ACID

| 特性 | 含义 |
|---|---|
| **原子性** Atomicity | 事务里的操作要么全做，要么全不做 |
| **一致性** Consistency | 事务前后数据库都满足完整性约束 |
| **隔离性** Isolation | 并发事务之间互不干扰 |
| **持久性** Durability | 提交后的结果永久生效，断电也不丢 |

### 隔离级别与三类读问题

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| 读未提交 Read Uncommitted | 可能 | 可能 | 可能 |
| 读已提交 Read Committed | 不可能 | 可能 | 可能 |
| 可重复读 Repeatable Read | 不可能 | 不可能 | 可能 |
| 串行化 Serializable | 不可能 | 不可能 | 不可能 |

- **脏读**：读到了别的事务还没提交、之后可能回滚的数据。
- **不可重复读**：同一事务内两次读同一行，结果不同（别人改了 / 删了）。
- **幻读**：同一事务内两次按条件查，第二次多出了"幻影"行（别人插了）。

> 级别越高越安全，但并发性能越低。多数数据库默认"读已提交"，MySQL InnoDB 默认"可重复读"。

### 封锁与两段锁

- **共享锁 S（读锁）**：可多人同时持有；加了 S 锁别人不能加 X 锁。
- **排他锁 X（写锁）**：独占，别人既不能读也不能写。

**两段锁协议（2PL）**：一个事务的加锁 / 解锁分成两个阶段——**扩展阶段只加锁，收缩阶段只解锁**。遵守 2PL 就能保证并发调度**可串行化**，代价是可能死锁。

- **活锁**：某个事务永远轮不到锁 → 用先来先服务解决。
- **死锁**：互相等对方持有的锁 → 预防（一次封锁法 / 按序封锁法）、诊断与解除（超时法 / 等待图法）。

## 简答题整理

### 1. 文件系统管理数据有哪些特点？

1. **数据可长期保存**：数据以文件形式存储在外存上，可反复存取。
2. **由文件系统统一管理**：操作系统中的文件系统负责数据的组织和存取，程序与数据之间有了一定的独立性。
3. **数据共享性差，冗余度大**：文件面向应用，不同应用的数据各自存储，造成大量重复数据。
4. **数据独立性差**：文件结构改变必须修改应用程序，程序与数据仍紧密耦合。
5. **数据结构化程度低**：文件内部有结构，但文件之间无联系，整体无结构。

### 2. 何为数据处理，何为数据管理？它们之间的关系如何？

| 概念 | 定义 |
|------|------|
| **数据处理** | 对数据进行收集、存储、加工、传播等一系列活动的总和，目的是从原始数据中提取有价值的信息。 |
| **数据管理** | 数据处理中的基本环节，指对数据进行分类、组织、编码、存储、检索和维护等操作。 |

**关系**：数据管理是数据处理的**组成部分和基础**，数据处理包含数据管理；数据管理的好坏直接决定数据处理的效率和质量。

### 3. 关系模式规范化主要解决哪几个方面的问题？

主要解决以下四种问题（统称为**数据冗余和操作异常**）：

1. **数据冗余**：同一数据重复存储，浪费空间。
2. **更新异常**：修改一处数据需改多处，易漏改导致数据不一致。
3. **插入异常**：某些信息因缺少主键值而无法插入（如没有学生时无法插入系信息）。
4. **删除异常**：删除某条记录时连带丢失其他应有的信息。

### 4. 数据库设计分为哪几个步骤？

按生命周期法，数据库设计分为**6个阶段**：

1. **需求分析**：收集和分析用户需求。
2. **概念结构设计**：绘制 E-R 图，建立概念模型。
3. **逻辑结构设计**：将 E-R 图转换为关系模式，并进行规范化。
4. **物理结构设计**：确定存储结构、索引、分区等物理参数。
5. **数据库实施**：建立数据库、编制与调试应用程序、数据载入。
6. **数据库运行和维护**：日常运行、性能监控、备份恢复、扩充修改。

## 速查表

| 想干什么 | 关键点 |
|---|---|
| 看到"全部 / all" | 想除法，或 SQL 的双重 `NOT EXISTS` |
| 看到"不 / 没有" | 想差集 `−` 或 `NOT IN` |
| 看到"至少 N 个" | 想自连接 / `GROUP BY ... HAVING COUNT(*) >= N` |
| 判范式 | 先找码，再看非主属性有没有部分 / 传递依赖 |
| 分解是否安全 | 查无损连接 + 保持依赖，二者可能冲突 |
| 选隔离级别 | 按能容忍哪种读问题来定，不是越高越好 |
